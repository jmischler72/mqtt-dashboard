# Product Requirement Document (PRD)

## Feature: Multi-Broker Support

**Module Name:** Multi-Broker Architecture & Config Workspace

**Status:** Ready for Architecture Review

---

## 1. Feature Overview & Objectives

As IoT environments scale, developers frequently need to orchestrate data across multiple disconnected environments simultaneously (e.g., a local home Mosquitto broker running on a Raspberry Pi alongside a cloud-hosted AWS IoT or HiveMQ production cluster).

This feature evolves mqtt-dashboard from a single-broker utility into a centralized multi-broker control tower. Users can register, reorder, and selectively toggle multiple concurrent broker instances. Individual dashboard panels can then be explicitly mapped to separate brokers, allowing a single dashboard interface to visualize cross-broker telemetry side-by-side.

## 2. Database & Backend Architecture Updates

To support multiple active connections simultaneously, the Go backend must shift from a singleton MQTT client pattern to a concurrent map-based tracking registry.

### 2.1. SQLite Schema Migrations

This section tell how to migrate but the agent should just rewrite the db.go migrate as there is no need to do a proper migration as told in Claude.md

The database schema must be refactored to decouple configuration profiles from a single static record, converting them into an identifiable, order-mapped collection.

```sql
-- 1. Upgrade mqtt_configurations to support named, multi-broker entries
CREATE TABLE IF NOT EXISTS mqtt_brokers (
    id TEXT PRIMARY KEY,               -- UUID generated by frontend or Go backend
    name TEXT NOT NULL,                -- User-defined profile label (e.g., "Home Assistant", "Cloud Staging")
    host TEXT NOT NULL,
    port INTEGER NOT NULL,
    client_id TEXT,
    username TEXT,
    password TEXT,
    is_enabled BOOLEAN DEFAULT 1,      -- Checkbox state tracker
    sort_order INTEGER NOT NULL        -- Determines list order and default election
);

-- 2. Update dashboard layouts to map a panel to a specific broker identifier
ALTER TABLE dashboard_layouts ADD COLUMN broker_id TEXT;
```

### 2.2. Data Mapping & Integrity Rules

- **UUID Mapping Rule:** Panels must strictly bind to a broker using its immutable `id` (UUID string), **never** by its visual index or sorting position. When a user drags to reorder brokers or flips the default choice, existing dashboard panels remain locked to their assigned broker without data corruption.
- **Default Option Fallback Logic:** The broker with `is_enabled = 1` holding the lowest `sort_order` values acts as the system default. When a user spawns a brand new panel on the Dashboard, the layout generation script automatically sets its internal `broker_id` parameter to this default broker.

### 4.1. Visual State Matrices

The indicator text and warning icons dynamically scale to match multi-client health statuses:

- **Connected (Green):** $100\%$ of internal broker profiles flagged as `is_enabled` are actively authenticated against their respective broker targets.
- **Partially Connected (Orange):** At least one enabled broker connection is alive, but one or more adjacent active connections are experiencing `DISCONNECTED` or validation timeouts.
- **Disconnected (Red):** All enabled connection profiles fail to communicate with any target broker instances.

### 4.2. Detailed Diagnostic Flyout Dropdown

Hovering mouse inputs over the primary header aggregation module opens an absolute target floating layout frame built natively using the DaisyUI dropdown wrapper utility. This lists each individual broker profile name alongside its real-time connection status.

## 5. Backend Connection Lifecycles (Go)

- **Parallel Client Instantiation:** On initialization, the backend queries `SELECT * FROM mqtt_brokers WHERE is_enabled = 1`. The Go core spins up separate go-routines using individual `paho.mqtt.golang` client configurations for each row entry.
- **Dynamic Lifecycle Updates:** When an API save event modifies a broker's `is_enabled` flag, the Go engine intercepts the state alteration event:
    - If shifted from **Disabled ➔ Enabled**, it creates a new client connection on the fly.
    - If shifted from **Enabled ➔ Disabled**, it gracefully disconnects the network sockets (`client.Disconnect(250)`) and drops the broker client from the active operational map memory.
