# Product Requirement Document (PRD)

## Automated Release Management & CI Verification

## 1. Overview & Objectives

Managing releases manually is error-prone, leads to inconsistent changelogs, and consumes valuable development time. This project aims to completely automate our versioning, changelog generation, and production deployment pipeline.

By enforcing **Conventional Commits** at the Pull Request (PR) level and leveraging Google's **`release-please`**, we will create a hands-off release system that triggers a secure production build and push to GitHub Packages (GHCR) upon merging a release.

### Core Goals

- **Enforce Structure:** Ensure all incoming code changes follow the Conventional Commits specification.
- **Automate Versioning:** Eliminate manual semantic versioning ($Major.Minor.Patch$) decisions.
- **Automate Documentation:** Generate clean, accurate `CHANGELOG.md` files automatically.
- **Continuous Deployment:** Build and deploy production Docker images to GHCR only when an official release is merged.

## 2. User Workflow & Architecture

The system relies on a strict branch lifecycle. The diagram below illustrates the exact flow from a developer's feature branch down to the final production image deployment.

`[ Developer Branch ]
         │
         ▼  (Verify PR Title via CI)
   [ Pull Request ] ───► Merged into `main`
         │
         ▼  (Triggers release-please)
[ Release-Please PR ] (Updates Changelog/Versions)
         │
         ▼  (Merged into `main`)
[ GitHub Release Tag ]
         │
         ▼  (Triggers Docker Build)
[ Production Image Pushed to GHCR ]`

## 3. Detailed Feature Requirements

### 3.1 PR Verification (Conventional Commits CI)

To ensure `release-please` can accurately calculate the next version, the gateway to the `main` branch must be strictly guarded.

- **Trigger:** Any pull request opened, updated, or reopened against the `main` branch.
- **Action:** A GitHub Actions workflow validates that the **PR Title** conforms to the Conventional Commits specification.
    - *Allowed Types:* `feat` (minor version bump), `fix` (patch version bump), `docs`, `style`, `refactor`, `perf`, `test`, `chore`.
    - *Breaking Changes:* Must contain a `!` after the type/scope or `BREAKING CHANGE:` in the description to trigger a major version bump.
- **Enforcement:** This CI check is **required to pass** before the PR can be merged.

### 3.2 Release Automation (`release-please`)

Once code hits `main`, automation takes over to prepare the next release package.

- **Trigger:** Any merge into the `main` branch.
- **Action:** `release-please` scans the new commit history since the last tag.
- **The Release PR:**
    - If changes warrant a version bump, `release-please` automatically opens/updates a special **Release PR** (e.g., `release-please--branches--main`).
    - This PR contains updates to `CHANGELOG.md`.
    - **Monorepo/Multi-component support:** It bumps the version strings inside configuration files for both the **Frontend** and **Backend** applications (e.g., `package.json`, `pom.xml`, or `cargo.toml` depending on your language).
- **Behavior:** As more feature PRs are merged into `main`, `release-please` will continuously update this open Release PR, stacking the changelog and adjusting the version bump accordingly.

### 3.3 Production Build & Push (CD Pipeline)

This pipeline only runs when a version is officially minted.

- **Trigger:** When the **Release PR** is merged into `main`. (Specifically targeting the creation of a GitHub Release/Tag generated by `release-please`).
- **Action:**
    1. Log in to GitHub Container Registry (`ghcr.io`) using the repository's `GITHUB_TOKEN`.
    2. Build the production Docker images for both Frontend and Backend.
    3. Tag the images with:
        - The specific release version (e.g., `v1.2.3`).
        - `latest` (to update the active production pointer).
    4. Push the tagged images to GHCR.

## 4. Configuration Requirements & Branch Protection

To make this workflow function seamlessly, the following settings must be applied to the GitHub Repository.

### Branch Protection Rules (`main` branch)

- [x]  **Require a pull request before merging:** Direct pushes to `main` must be blocked.
- [x]  **Require status checks to pass before merging:** The Conventional Commits CI check must pass.
- [x]  **Allow bypass completions:** `release-please` actions/tokens must be allowed to push updates to the release branch.

### GitHub Actions Permissions

- The workflow GITHUB_TOKEN must be granted `write` permissions for `contents` (to create releases and tags) and `pull-requests` (to open and update the release PR).

## 5. Proposed Technology Implementation

While implementation specifics can iterate, the standard tooling to satisfy this PRD involves two GitHub Action workflows:

1. **`verify-pr.yml`:** Utilizing an action like `amannn/action-semantic-pull-request` to validate PR titles.
2. **`release.yml`:** Running `google-github-actions/release-please-action` as step one, followed by a conditional step using `docker/build-push-action` that executes **only** if `release-please` outputs `release_created === true`.

## 6. Success Metrics & Verification Checklist

Before signing off on this feature release, the following scenarios must be verified in a test environment:

- [ ]  Creating a PR with the title `bad title: fixed some stuff` is successfully blocked by CI.
- [ ]  Creating a PR with the title `fix: resolve memory leak in backend` passes CI.
- [ ]  Merging a valid PR to `main` results in `release-please` opening a Release PR within 1-2 minutes.
- [ ]  The Release PR correctly contains version bumps in target frontend/backend files and a new entry in `CHANGELOG.md`.
- [ ]  Merging the Release PR automatically creates a GitHub Release Tag and triggers the Docker workflow.
- [ ]  Final images are visible and pullable from GHCR with the correct semantic tags.
